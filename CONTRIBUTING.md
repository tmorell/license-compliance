## Code of Conduct

This project aims to foster an open and welcoming environment. Please treat all contributors with respect, courtesy, and empathy.

## Security Disclosures

If you discover a potential security vulnerability within `license-compliance`, please **do not** open a public issue. Instead, report it using [GitHub's private vulnerability reporting](https://github.com/tmorell/license-compliance/security/advisories/new), which keeps the report tracked and out of the public issue tracker.

If you're unable to use that flow, you can alternatively email the maintainer at [teomorell@gmail.com](mailto:teomorell@gmail.com), though private reporting is preferred.

## How Can I Contribute?

### Reporting Bugs

Before creating a bug report, please check existing issues to ensure it hasn't already been reported.

When opening a bug report, use the [Bug Report Template](.github/ISSUE_TEMPLATE/bug_report.md) and include:

- **Clear Title**: A concise summary of the issue.
- **Steps to Reproduce**: Detailed steps showing how to reproduce the behavior.
- **Expected vs Actual Behavior**: What you expected to happen versus what actually happened.
- **Environment**: Node.js version, OS, package version, and package manager used.

### Suggesting Enhancements

Feature requests and enhancements are always welcome. Please use the [Feature Request Template](.github/ISSUE_TEMPLATE/feature_request.md) to explain:

- The problem or limitation you are encountering.
- Your proposed solution or desired feature.
- Any alternative workarounds considered.

### Where to Start

New to the project? Look for issues labeled [`good first issue`](https://github.com/tmorell/license-compliance/issues) — these are scoped to be approachable without deep familiarity with the codebase. If nothing is labeled, feel free to open an issue describing what you'd like to work on before starting, so the approach can be discussed first.

### Pull Requests

1. Fork the repository and create a feature branch off `master` (e.g., `feat/short-description` or `fix/short-description`).
2. Ensure your code conforms to the existing style, passes linting, formatting, and all unit tests.
3. Make atomic, focused commits with [Conventional Commit](#commit-message-guidelines) messages.
4. Verify your changes locally using `npm run all`.
5. Open a Pull Request targeting the `master` branch with a clear title and description. Before requesting review, confirm:
    - [ ] `npm run all` passes locally.
    - [ ] Tests are added or updated for any behavior change.
    - [ ] `README.md` is updated if CLI flags, options, or output formats changed.
    - [ ] The PR description links any related issue.

## Development Setup

### Prerequisites

- **Node.js**: `>= 20.0.0` (enforced via `engines` in `package.json`)
- **npm**: a recent version bundled with a supported Node.js release is sufficient; the project does not currently pin a minimum npm version.

### Installation

Clone your fork and install dependencies using `npm ci`:

```bash
git clone https://github.com/YOUR_USERNAME/license-compliance.git
cd license-compliance
npm ci
```

### Project Structure

```
license-compliance/
├── bin/            # CLI binary entry point (bin/cli.js)
├── lib/            # Compiled JavaScript output (generated by build)
├── src/            # TypeScript source code
│   ├── formatters/ # Output formatters (text, json, csv, xunit)
│   ├── reports/    # Report types (detailed, summary)
│   ├── index.ts    # Library entry point
│   ├── main.ts     # Main application execution logic
│   └── ...
├── tests/          # AVA test suites and mock package fixtures
├── eslint.config.mjs
├── package.json
├── tsconfig.build.json
└── tsconfig.json
```

## Available Scripts & Workflow

All development commands are defined in [`package.json`](package.json).

### Building

Compile TypeScript source code in `src/` to ES modules in `lib/`:

```bash
npm run build
```

_(This automatically cleans `./lib` and `./coverage` before transpiling via `tsc`.)_

### Testing & Coverage

Run unit tests with AVA:

```bash
# Type-check only
npm run typecheck

# Run type check and unit tests
npm run test

# Run tests in watch mode
npm run test:watch

# Type-check, then run tests with code coverage (c8)
npm run test:ci

# Generate an HTML coverage report and open it in your browser
# (downloads the `open-cli` package on first run via npx)
npm run coverage

# Generate an lcov coverage report (used by CI for coverage reporting services)
npm run coverage:ci
```

> **Note**: `npm run test:ci` runs `typecheck` before generating coverage — a type error will fail this step even if the tests themselves pass.

### Linting & Formatting

Verify code quality and formatting standard:

```bash
# Run ESLint
npm run lint

# Run ESLint with auto-fix
npm run lint -- --fix

# Check formatting with Prettier
npm run prettier
```

### Circular Dependency Check

Check for circular module imports using `madge`:

```bash
npm run circular
```

### Full CI Pipeline Verification

Before pushing changes or submitting a Pull Request, run the complete verification script that mirrors CI:

```bash
npm run all
```

This single command executes build, circular dependency check, linting, prettier formatting, and unit tests with code coverage.

## Commit Message Guidelines

This repository follows [Conventional Commits](https://www.conventionalcommits.org/). Commit messages should be structured as follows:

```
<type>(<optional scope>): <description>
```

> **Note**: These conventions are currently enforced by reviewer discretion rather than an automated commit linter, so please double-check your message format before pushing.

### Allowed Types

- `chore`: Maintenance, tooling, or configuration changes.
- `docs`: Improvements or additions to documentation.
- `feat`: New functionality or request.
- `fix`: Something isn't working correctly.
- `perf`: Changes that improve execution speed or resource usage.
- `refactor`: Code changes that neither fix a bug nor add a feature.
- `test`: Adding missing tests or correcting existing tests.

### Examples

- `chore: update dependencies`
- `docs: update installation instructions in README.md`
- `feat: add support for custom SPDX license overrides`
- `fix: handle missing license field in legacy package.json`
